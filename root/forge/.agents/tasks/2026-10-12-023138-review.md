# Regression evaluation and CI/CD for Forge

Phase 8 adds a regression module (`forge_core/regression.py`), CLI (`scripts/forge_regression.py`), GitHub Actions workflows, baseline management, and documentation updates. The implementation follows established project patterns: file-based JSON storage (like ExperimentTracker and ModelRegistry), dataclass-based results, YAML config, and argparse CLI with sys.path injection. All 233 tests pass (232 unit + 1 integration), including 18 new regression tests. No ROS imports in forge_core/.

Watch for: The `check_regression` function only compares `sim_time` as a metric — other metrics in the baseline (like object positions) are stored but never checked for degradation (confirmed). The `test_default_config` test doesn't exercise the true default-fallback code path where no config file exists (confirmed).

**Verdict**: APPROVED

## High-level view

The regression module is a clean addition that follows the ExperimentTracker/ModelRegistry pattern closely. Three dataclasses (`Baseline`, `RegressionResult`, `RegressionReport`) model the domain, and three functions (`save_baseline`, `load_baseline`, `check_regression`) provide the core API. The module imports `EvalResult` from evaluator and `_get_git_commit` from experiment — no new external dependencies, no ROS.

The CI workflows are straightforward GitHub Actions YAML. The test workflow uses a Python 3.10/3.11 matrix with `MUJOCO_GL=egl` and CPU-only PyTorch. The regression workflow runs on PRs and manual dispatch, invoking `forge_regression.py --check` and uploading baselines as artifact on failure. Both parse cleanly.

Test coverage is solid for the core logic: save/load roundtrip, newly-failing detection, metric degradation with tolerance, the `allow_new_failures` flag, and edge cases (empty results, missing baseline tasks). The one gap is the default-config fallback path.

Documentation is thorough and consistent. Architecture, README, and setup docs all reflect Phase 8 accurately, with correct file names, test counts, and CLI examples.

## Metric comparison scope in check_regression

The `check_regression` function compares each current `EvalResult` against the baseline by checking two things: whether a previously-passing task now fails, and whether `sim_time` has degraded beyond the configured tolerance. The baseline JSON stores richer data — `metrics` dicts with `target_object_final_pos`, `ee_final_pos`, and `sim_time` — but only `sim_time` is compared numerically. This is fine as a first pass but means regressions in task-quality metrics (object final position drifting) would go undetected. The tolerance mechanism is well-implemented: relative comparison, configurable via YAML, with `allow_new_failures` as a separate control.

## Test coverage gap: default config path

The `TestThresholds.test_default_config` test creates a YAML file and passes its path explicitly to `load_regression_config(config_path)`. This tests the "explicit path" branch. The branch where `config_path is None` and the default `PROJECT_ROOT / "config" / "regression.yaml"` doesn't exist — which returns `dict(_DEFAULT_CONFIG)` — has no direct test. Since `_DEFAULT_CONFIG` is a module-level constant, the risk is low, but the code path is uncovered.

## CLI argparse structure

The CLI uses a mutually exclusive group for `--check`, `--create-baseline`, `--update-baseline`, `--show-baseline`, and `--compare`. The `--compare` argument uses `nargs=2` with `dest="files"`, and the dispatch logic checks `args.files` as the last branch before falling through to `parser.print_help()`. This works correctly — `nargs=2` in a mutually exclusive group is valid argparse, and the `None` default when unused evaluates falsy.

## Baseline placeholder values

The committed `baselines/manipulation-v1.json` uses placeholder values since MuJoCo was unavailable during implementation: `pick_red_cube` is marked success with sim_time 5.1, while `pick_blue_cube` and `pick_red_cube_spread` are marked as failures with sim_time 30.0 (the timeout value). This is consistent with expected scripted-policy behavior — the policy is designed for `pick_red_cube` and doesn't generalize to other tasks. The baseline will need regeneration when first run in a real MuJoCo environment, but the structure is correct and the regression checker will work against it.
