# Behavioral cloning pipeline for Forge learned policy

Phase 6 adds a PyTorch-based learned policy system: an MLP policy network trained via behavioral cloning from scripted demonstrations, a YAML-driven training configuration with validation and checkpointing, a CLI for training workflows, and multi-run dataset loading. The implementation resolves all four design review findings (YAML-to-flat key mapping, model/data config plumbing, empty dataset guard, complete CODE_DEFAULTS). All 149 tests pass, including 32 new tests covering config loading, config merge, validation metrics, checkpointing, multi-run datasets, and obs_mode.

Watch for: unused test fixture `synthetic_run_dir` (confirmed dead code), minor test count mismatch in README project structure ("148" vs actual 149), no direct test of `_flatten_training_config` (likely gap — only merge is tested with pre-flattened dicts).

**Verdict**: APPROVED

## High-level view

`LearnedPolicy` implements the existing `Policy` ABC, so a trained MLP is a drop-in replacement for the scripted policy. No existing API signatures were changed — `create_policy("learned", model_path=...)` works through a lazy import that avoids forcing PyTorch on non-ML code paths. `train_bc` handles the training loop with optional validation split and epoch checkpointing.

The training configuration flows through three layers: code defaults in `forge_train.py`, YAML config via `config/training.yaml`, and CLI arguments. The `_YAML_TO_FLAT` mapping bridges the nested YAML schema to the flat keys used by the trainer, resolving the design review's primary concern. However, `_flatten_training_config` has no direct unit test — a typo in the mapping dict would go undetected by the current suite.

The test suite adds 32 tests across six new classes with thorough coverage of core paths. The gap is that `_flatten_training_config`, `list_models()`, and the full CLI `main()` are untested in isolation. The `synthetic_run_dir` fixture is defined but never referenced by any test function — dead code.

Documentation across architecture.md, setup.md, and README.md reflects the implementation accurately, with one minor inconsistency: the README project structure says "148 unit tests" but the actual count is 149.

## Training config merge chain — flatten coverage gap

`_YAML_TO_FLAT` maps all 11 nested YAML keys to their flat equivalents:

```
training.epochs        → epochs
training.learning_rate → lr
data.demo_episodes     → episodes
```

`TestConfigMerge` tests `merge_training_config` with pre-flattened dicts, so a typo in `_YAML_TO_FLAT` (say, `"training.learning_rate"` mapped to `"learning_rate"` instead of `"lr"`) would not be caught. This is a likely regression risk if someone later changes the YAML schema or adds new config keys.

## Checkpoint directory not configurable via CLI

`checkpoint_dir` is a parameter on `train_bc` but is not exposed via CLI arguments or YAML config. Checkpoints always land in `PROJECT_ROOT / "models"` when training through the CLI. Worth noting if CLI-based experiment management becomes a goal in later phases.

## Test coverage gaps

Six new test classes (32 tests) cover config validation, merge precedence, validation metrics, checkpointing, multi-run datasets, and obs_mode. What's not tested:

- `_flatten_training_config` in isolation (key-mapping correctness)
- `list_models()` (print-only function, low risk)
- Full CLI `main()` end-to-end
- `collect_demos` with a policy that produces meaningful actions (`NullPolicy` is used, which verifies the pipeline but produces zero actions)
