# Experiment tracking and model registry for Forge ML pipeline

Phase 7 adds two new `forge_core` modules — `experiment.py` and `model_registry.py` — that provide file-based experiment tracking and model versioning with zero external dependencies. These are wired into the existing training, evaluation, and runner pipeline, plus a new `forge_registry.py` CLI for management. The implementation follows the project's established patterns: dataclasses, `PROJECT_ROOT` path resolution, sequential ID generation mirrored from `recorder.py`, JSON persistence, and `logging.getLogger(__name__)`. All 215 tests pass (66 new), including the original 149.

Watch for: The `try/except` boundary in `train_bc()` wraps the entire training body including input guards, so even early `ValueError` from validation (empty dataset, bad split) gets reported as a "failed experiment" — this is deliberate and tested (confirmed). No blocking concerns found.

**Verdict**: APPROVED

## High-level view

The experiment tracker stores one JSON file per experiment under `experiments/exp_XXXXX.json`, using the same sequential ID pattern as `recorder.py`. Each experiment transitions through `running → completed | failed`, capturing config, dataset info, git commit, metrics, and model path. The model registry stores all entries in a single `registry/registry.json` file and enforces a stage lifecycle (`training → validated → production → archived`, with `archived → validated` for re-activation). Stage transitions are validated against an explicit `STAGE_TRANSITIONS` map, and illegal moves raise `ValueError`.

The integration layer passes an `ExperimentTracker` instance and `experiment_id` into `train_bc()` as optional parameters, using `Any` typing to avoid a hard import. The `forge_train.py` script wraps all tracking and registry calls in their own `try/except` blocks so tracking failures never crash training. The `--no-track` flag disables both experiment logging and model registration.

`forge_eval.py` gains `--registry-model` and `--registry-version` flags that resolve a checkpoint path from the registry and implicitly set the policy to `learned`. The `runner.py` adds a `load_policy_from_registry()` convenience function with lazy imports. The `forge_registry.py` CLI provides `experiments list|show|compare|delete` and `models list|show|promote|delete` subcommands with `--force` or interactive confirmation on deletes.

## Test coverage

66 new tests across three files:

- **ExperimentTracker** (20 tests): creation, sequential IDs, name/tags, git commit capture (monkeypatched), complete/fail lifecycle, listing with status/tag filters, timestamp sorting, comparison, deletion, error cases.
- **ModelRegistry** (18 tests): registration, auto-versioning, experiment ID and metadata, retrieval by name/version/stage, listing with filters and sorting, all valid stage promotions, invalid promotion (training→production), deletion, error cases.
- **Integration** (28 tests): train_bc with tracker creates completed record, validation metrics recorded, failed training marks experiment, backward compatibility (no tracker), tracker-without-experiment-id skipped, register-after-training links correctly, checkpoint path resolution, load_policy_from_registry, multiple version registration, and full CLI argument parsing for all 16 subcommand variations.

Not tested: `forge_train.py` end-to-end (requires simulation), `forge_eval.py` registry loading end-to-end (requires simulation), `forge_registry.py` interactive delete confirmation (requires stdin mocking).
