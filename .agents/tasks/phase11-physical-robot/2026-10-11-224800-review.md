# Physical Robot Support — Hardware Abstraction, Safety, Sim-to-Real

Phase 11 adds a hardware abstraction layer (`RobotInterface` ABC with `SimulatedRobot` implementation), a real-time safety monitor that gates commands against joint, velocity, and workspace limits, and sim-to-real transfer utilities (domain randomization, trajectory comparison, calibration). A CLI ties it all together. The implementation follows existing project conventions — dataclass style, config loading via `load_yaml`, test class grouping, argparse CLI — and integrates cleanly with the simulation, policy, and recorder subsystems.

Watch for: velocity estimation in `SafetyMonitor.check_command` uses position delta as a proxy for velocity without dividing by a time interval (confirmed). `safe_send_command` in `SafetyMonitor` does not trigger e-stop on repeated violations — it silently blocks commands (confirmed). `calibrate_workspace` stores a translation vector in `joint_offsets` field, which is semantically misleading (confirmed).

**Verdict**: APPROVED

## High-level view

The hardware abstraction is well-layered. `RobotInterface` defines six abstract methods (connect, disconnect, get_state, send_command, emergency_stop, get_status) and `SimulatedRobot` implements them by wrapping `ForgeSimulation`. The ABC is minimal and extensible — a real hardware driver would implement the same six methods. `run_policy_on_robot` bridges the policy loop to the hardware interface, reusing the internal sim when the robot is a `SimulatedRobot`.

The safety system intercepts commands before they reach hardware. `SafetyMonitor` checks joint limits, velocity (estimated from position delta), and workspace boundaries, returning structured `SafetyViolation` objects. The velocity check compares position delta directly against velocity limits without dividing by dt, which means the threshold's physical meaning depends on the control rate — this works for the current simulated setup but would need adjustment for real hardware with different control frequencies.

Sim-to-real transfer covers three concerns: domain randomization (gravity, friction, mass perturbation on the MuJoCo model), trajectory comparison (RMSE and correlation between sim and real joint/EE trajectories), and calibration (mean-offset joint calibration and centroid-based workspace alignment). These are pure numerical utilities operating on numpy arrays, easy to test and extend.

Test coverage is strong: 22 hardware tests, 18 safety tests, 16 sim2real tests — all 56 passing. The tests cover dataclass roundtrips, lifecycle, safety violation detection, calibration accuracy, and config loading. Documentation in architecture.md, setup.md, and README.md is thorough and consistent with the implementation.

## Velocity estimation as position delta

In `safety.py`, the velocity check at lines computing `delta = abs(cmd.joint_targets[i] - current_state.joint_positions[i])` compares this raw position difference against `velocity_limits`. The config names these "velocity_limits" and the YAML stores values like 2.2 rad/s, but the check doesn't divide by any time interval. For `SimulatedRobot` running at a fixed `steps_per_command` rate this happens to produce consistent behavior, but the safety contract is misleading: a target 2.3 rad away triggers a "velocity violation" regardless of whether the robot will take 1ms or 1s to get there. A real hardware driver with a different control frequency would need different limit values for the same physical velocity constraint.

## No e-stop escalation on repeated violations

`safe_send_command` returns `(False, violations)` when a command fails safety checks, but the caller (including `run_policy_on_robot`) just increments a counter and continues to the next policy step. There's no mechanism to trigger `emergency_stop()` after N consecutive blocked commands. In `run_policy_on_robot`, the code checks `status.status == "e_stopped"` after a failed send, but nothing in the safety monitor ever sets that status — only an explicit call to `emergency_stop()` does. In a real deployment, a policy that keeps requesting unsafe commands should be stopped, not allowed to spin indefinitely producing blocked commands.

## `calibrate_workspace` field semantics

`calibrate_workspace` computes a 3D translation and stores it in both `workspace_transform[:3, 3]` (correct) and `joint_offsets` (misleading). The `CalibrationResult` dataclass documents `joint_offsets` as `(n_joints,)` but receives a `(3,)` translation vector. Code consuming a `CalibrationResult` from `calibrate_workspace` would need to know which function produced it to interpret `joint_offsets` correctly.

## `run_policy_on_robot` coupling to SimulatedRobot internals

```python
if isinstance(robot, SimulatedRobot) and robot._sim is not None:
    sim = robot._sim
else:
    sim = ForgeSimulation("basic_workspace")
    sim.reset()
```

This is pragmatic for the current single-implementation scenario, but it means the "generic" policy runner function imports and inspects a specific implementation class. The alternative path (creating a fresh `ForgeSimulation("basic_workspace")`) would run the policy against a sim that's out of sync with the actual robot state, which is a correctness issue for real hardware. A cleaner approach would be to expose the shadow sim through the `RobotInterface` or accept it as a parameter.

## Test coverage

22 hardware tests cover all three dataclasses (creation, serialization, roundtrip), `SimulatedRobot` lifecycle (connect, disconnect, double-connect, send while disconnected, e-stop), ABC enforcement, and `run_policy_on_robot` with null policy, safety monitor, recorder, max steps, and summary keys.

18 safety tests cover `SafetyConfig` defaults and loading, `SafetyViolation` creation and serialization, and `SafetyMonitor` for all three violation types (joint, velocity, workspace), `is_safe` true/false, `safe_send_command` send/block paths, e-stop delegation, violation log accumulation, and custom config.

16 sim2real tests cover `DomainRandomizationConfig` defaults and from_dict, `apply_domain_randomization` with default and fixed configs, trajectory comparison (identical, different, truncation, to_dict), calibration (known offset, known translation, noisy data, to_dict), and config loading (defaults, real file, missing file).

Not tested: `run_policy_on_robot` with a policy that triggers e-stop via repeated safety violations. The CLI (`forge_robot.py`) subcommands are not unit-tested, though this is consistent with the project's pattern of not testing CLI scripts directly.
